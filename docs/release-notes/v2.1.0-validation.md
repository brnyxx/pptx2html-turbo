# v2.1.0 Validation Report

Prepared on 2026-09-01 from branch `feature/multiformat-v2.1-release`.

This report records the local release-candidate boundary for v2.1.0. It separates evidence
that can be reproduced from the repository, external proxy evidence, unavailable
PowerPoint-native evidence, and publication actions that still require explicit human
authorization.

## Release Decision

The candidate is ready for the versioned release workflow. The remaining actions are external:
publishing the branch, integrating it into `main`, creating tag `v2.1.0`, and allowing the
tag-triggered GitHub Release and npm workflows to run. None of those actions was performed
while preparing this report.

v2.1.0 remains an approximate/high-fidelity release. It does not claim Microsoft Office pixel
accuracy, PowerPoint pixel equality, byte-identical output, or a PPTX `exact` tier.

## Browser and Demo Evidence

The packaged WASM facade converted the two-slide fixture in Chromium. The GitHub Pages demo
converted `single-slide.pptx` on desktop and mobile, displayed the converted slide inside the
opaque-origin frame, emitted no browser console errors, and produced no horizontal overflow.
An input above 64 MiB was rejected before `arrayBuffer()` was called.

The release closure keeps that rendered design unchanged and adds only non-visual deployment
metadata and release destinations. Fresh 375px, 768px, and 1280px captures and their cleanup
receipts are stored under `.omo/evidence/release-docs-final/browser/`.

## PowerPoint-Native Exactness Boundary

The required PowerPoint-native text-layout deck set is incomplete. Eleven native reference

## Publication Boundary

Read-only checks on 2026-09-01 found all release destinations absent:

- remote branch `feature/multiformat-v2.1-release`;
- remote tag `v2.1.0`;
- npm `@briank-dev/pptx-to-html@2.1.0`;
- npm `@briank-dev/pptx2html-turbo@2.1.0`.

Repository workflow behavior defines the authorized publication sequence:

1. Publish and integrate the reviewed release branch into `main` after human approval.
2. Create and push `v2.1.0` only after the merged commit and version contract are confirmed.
3. The tag triggers `.github/workflows/release.yml` and
   `.github/workflows/publish-npm.yml`; wait for both to complete before declaring the release
   published.
4. The `main` update triggers `.github/workflows/deploy-demo.yml`; confirm the Pages URL loads
   the v2.1.0 demo and its `releases/latest` destination resolves to the published release.
5. Record remote workflow URLs, release/npm availability, and the deployed Pages smoke as
   post-publication receipts. Local dry-runs are not substitutes for those receipts.

The [pre-release checklist](./pre-release-checklist.md) remains the operator gate for these
actions.
